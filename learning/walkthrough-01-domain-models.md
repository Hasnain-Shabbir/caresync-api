## 1. The goal
GraphQL needs more than one type before nested queries make sense (`organization { patients { ... } }`). So we add the two core records of CareSync:
- **User**: someone who logs in (staff of an organization).
- **Patient**: a person receiving care, owned by one organization.

Both belong to an `Organization` (the tenant). This is the foundation for multi-tenancy later: every row says which organization it belongs to.

---

## 2. How the files were generated
```
bin/rails generate model User organization:references email:string password_digest:string \
  first_name:string last_name:string role:string --no-test-framework
bin/rails generate model Patient organization:references first_name:string last_name:string date_of_birth:date --no-test-framework
```
- `generate model` creates a migration and an empty model class. `--no-test-framework` skips auto-generated test and fixture files, because we wrote our own.
- `organization:references` creates an `organization_id` column plus an index and a foreign key.
- The generator gives loose columns (all nullable). **We then edited the migrations by hand** to add constraints. That edit is the important part, see below. We could edit them freely because they hadn't been run yet.

Then `bin/rails db:migrate` ran both and rewrote `db/schema.rb`.

## 3. The migrations, line by line

### `create_users`
```ruby
create_table :users do |t|
  t.references :organization, null: false, foreign_key: true
  t.string :email, null: false
  t.string :password_digest, null: false
  t.string :first_name, null: false
  t.string :last_name, null: false
  t.string :role, null: false, default: "front_desk"

  t.timestamps

  t.index :email, unique: true
end
```
- `t.references :organization, null: false, foreign_key: true`: creates `organization_id` (bigint, NOT NULL), an index on it, and a **foreign key** to `organizations(id)`. Postgres will refuse a user whose organization doesn't exist, and refuse deleting an organization that still has users (unless we handle it, see section 6).
- `null: false` on every required column means the **database** rejects missing values, even if someone bypasses the Rails model (console, `update_all`, a future script).
- `password_digest`: where `has_secure_password` stores a bcrypt hash. It is a hash, **never the password**. Added now so we don't need another migration in the auth step. (The `bcrypt` gem comes then.)
- `role` with `default: "front_desk"`: the lowest-privilege role is the default. "Safe by default" is a security habit: forgetting to set a role never creates an admin.
- `t.timestamps`: `created_at` and `updated_at`, filled automatically.
- `t.index :email, unique: true`: the real guarantee that two users never share an email. The model validation can't guarantee this alone, because two simultaneous requests can both pass the check before either saves (a race).

### `create_patients`
```ruby
create_table :patients do |t|
  t.references :organization, null: false, foreign_key: true
  t.string :first_name, null: false
  t.string :last_name, null: false
  t.date :date_of_birth, null: false

  t.timestamps

  t.index [ :organization_id, :last_name, :first_name ]
end
```
- A **composite index** on `[organization_id, last_name, first_name]` speeds up "patients of this organization sorted or searched by name". Postgres can use it for queries filtering on `organization_id` alone, or `organization_id` + `last_name`, in that left-to-right order. It can't help a query on `last_name` alone.
- Because every real query will be tenant-scoped (`WHERE organization_id = ?`), putting `organization_id` first is the right order.

### What `db/schema.rb` shows afterwards
The schema file is a readable snapshot of the real database. It now lists `users`, `patients`, their indexes, and the two `add_foreign_key` lines. Commit it, but don't edit it. To rebuild from scratch: `bin/rails db:schema:load`.

### Things to try
- `bin/rails dbconsole`, then `\d users` to see the columns, indexes and foreign key as Postgres sees them.
- `bin/rails db:rollback` undoes the last migration. `bin/rails db:migrate` redoes it. (Rollback works because `change` is reversible.)

## 4. The models, line by line

### `Organization`
```ruby
class Organization < ApplicationRecord
  has_many :users, dependent: :restrict_with_exception
  has_many :patients, dependent: :restrict_with_exception

  validates :name, presence: true, uniqueness: true
end
```
- `has_many :users` adds `organization.users`, a query for `users` rows with that `organization_id`. Also `organization.users.create!(...)`, which fills `organization_id` for you.
- `dependent: :restrict_with_exception` controls what happens on `organization.destroy`. It **refuses**, raising `ActiveRecord::DeleteRestrictionError`, if any users (or patients) exist. The alternatives are `:destroy` (deletes the children too) and nothing (the database's foreign key blocks it with a less friendly error). For health data, a silent cascade delete is dangerous, so we block it.

### `User`
```ruby
class User < ApplicationRecord
  belongs_to :organization

  enum :role, {
    admin: "admin",
    provider: "provider",
    nurse: "nurse",
    front_desk: "front_desk"
  }, validate: true

  normalizes :email, with: ->(email) { email.strip.downcase }

  validates :email, presence: true,
                    uniqueness: true,
                    format: { with: URI::MailTo::EMAIL_REGEXP }
  validates :first_name, :last_name, presence: true
end
```
- `belongs_to :organization`: the other side of `has_many`. In Rails 5+ it is **required** by default, so a user without an organization is invalid with no extra validation line.
- `enum :role, {...}`: maps names to stored values. It gives `user.admin?`, `user.nurse!` (changes and saves), and scopes like `User.admin`. We use **string values** so the column is readable in SQL (`role = 'admin'`) instead of magic numbers.
- `validate: true`: an unknown role (e.g. `"superuser"`) becomes a normal validation error, not an `ArgumentError` crash. That matters later, when role comes from GraphQL input.
- `normalizes :email, with: ->(email) { ... }`: runs on assignment (and on finders like `User.find_by(email: ...)`). `"  Mixed@Sunrise.TEST "` is stored as `"mixed@sunrise.test"`. The `->(x) { ... }` is a **lambda**, an anonymous function (like `x => ...` in JS).
- Why normalize? Without it, `Ada@x.com` and `ada@x.com` are two accounts, and login would fail depending on how someone types their email.
- `validates :email, presence: true, uniqueness: true, format: {...}`: friendly errors before hitting the database. `URI::MailTo::EMAIL_REGEXP` is Ruby's built-in email pattern. Not perfect, but a good basic check. The unique index (migration) is the safety net behind `uniqueness: true`.
- `validates :first_name, :last_name, presence: true`: one line for two attributes.
- There is no password validation yet, since `has_secure_password` arrives in the authentication step.

### `Patient`
```ruby
class Patient < ApplicationRecord
  belongs_to :organization

  validates :first_name, :last_name, :date_of_birth, presence: true
end
```
Same ideas. (Later steps add encryption for PHI fields, audit logging, and tenant scoping.)

## 5. Fixtures (sample test data)

`test/fixtures/users.yml` and `patients.yml` are YAML files loaded into the test database before each test run. Each top-level key (`admin_sunrise`, `alice`) is a **label**.

```yaml
admin_sunrise:
  organization: sunrise          # a LABEL from organizations.yml, Rails resolves the id
  email: admin@sunrise.test
  password_digest: "placeholder"
  ...
```
- `organization: sunrise` is the association shortcut: instead of an id number, use the label. Rails computes the same id from the label everywhere.
- In tests you read them with `users(:admin_sunrise)`, `patients(:alice)`, `organizations(:sunrise)`.
- **Design choice:** only `sunrise` has users and patients. `valley` stays empty on purpose, so we have one organization that can be deleted (tests for destroy) and one that cannot.
- `password_digest: "placeholder"` is fake. In the auth step we replace it with a real bcrypt hash.

## 6. The REST side effect, and the 409 handler

### What broke
`DELETE /api/v1/organizations/:id` calls `destroy!`. Now that `sunrise` has users and patients, `destroy!` raises `ActiveRecord::DeleteRestrictionError`. Nothing handled that, so the old destroy test failed with an error. In a real request that would have been a **500 Internal Server Error**, which is wrong: it's the client's request that conflicts with the data, not a server bug.

### The fix: one more `rescue_from` (same pattern as before)
In `ApplicationController`:
```ruby
rescue_from ActiveRecord::DeleteRestrictionError, with: :render_conflict

def render_conflict(exception)
  render json: {
    error: {
      code: "conflict",
      message: "Cannot delete this record because other records depend on it"
    }
  }, status: :conflict
end
```
- **409 Conflict** is the standard status for "the request is valid but conflicts with the current state of the resource".
- We wrote our own message, not `exception.message`, so we never expose internals (good habit for PHI).
- This is exactly the "how to add more error handling" recipe from [rescue-from-error-handling.md](rescue-from-error-handling.md): exception class, `rescue_from` line, private handler method, same envelope.

### Test changes in the controller test
- "destroy removes the organization and returns 204" now deletes `organizations(:valley)` (the empty one).
- New test: "destroy returns 409 when the organization still has users or patients" deletes `sunrise`, asserts the count didn't change, and checks `error.code == "conflict"`.

## 7. The tests, explained

### `UserTest`
- `build_user(**overrides)` is a helper: builds a valid `User` with default attributes, merged with any overrides. `**overrides` collects keyword arguments into a hash. Each test then changes just the attribute it cares about. (Pattern: "one valid baseline, break one thing at a time".)
- `assert build_user.valid?`: the baseline is valid.
- `assert_not build_user(email: nil).valid?`: presence check.
- Normalization test: assigns `"  Mixed@Sunrise.TEST "`, expects `"mixed@sunrise.test"`.
- Uniqueness tests: the second one uses `"ADMIN@sunrise.test"` to prove normalization plus uniqueness catch case differences.
- Role tests: an unknown role is invalid (`validate: true`), and the default role is `front_desk` (`.front_desk?` is generated by the enum).

### `PatientTest`
- Valid baseline, then each required field missing (`first_name`, `last_name`, `date_of_birth`), and the association.

### `OrganizationTest` (added)
- `has many users and patients`: `sunrise` has 2 of each (counting the fixtures).
- `cannot be destroyed while it has patients`: `assert_raises(ActiveRecord::DeleteRestrictionError) { ... }` passes only if that exact exception is raised.
- `can be destroyed when it has no users or patients`: `valley` can go, and the count drops by 1 (`assert_difference("Organization.count", -1)`).

## 8. Concepts to be able to explain (self-check, with answers)

1. **Why a unique index and `validates uniqueness`?** Validation gives a friendly error early. The index is the real guarantee, because two concurrent requests can both pass the validation check, and only the database can stop the second insert.
2. **What does `t.references :organization, foreign_key: true` create?** An `organization_id` bigint column, an index on it, and a foreign key constraint to `organizations(id)`. With `null: false` the column is also required.
3. **A patient insert with a nonexistent `organization_id`?** The DB foreign key rejects it (`ActiveRecord::InvalidForeignKey`). Through Rails models, `belongs_to` validation fails first, with "Organization must exist".
4. **`destroy!` on an organization with patients?** With `dependent: :restrict_with_exception`: `DeleteRestrictionError` before touching the DB. Without `dependent:`: the DB foreign key blocks it with `InvalidForeignKey`. With `dependent: :destroy`: the patients would be deleted too, which is dangerous for PHI.
5. **Why `has_many` on Organization and `belongs_to` on Patient?** The foreign key column (`organization_id`) lives in the patients table, so Patient "belongs to" the organization. Organization "has many" patients.
6. **Why return 409 and not 500 for the restricted delete?** 5xx means the server failed. Here the server worked correctly and refused a request that conflicts with the data, which is a client-visible 4xx condition.
7. **Why a default role of `front_desk`?** Least privilege: a forgotten role should never grant power.
8. **Why does the enum use `validate: true`?** An invalid role becomes a normal validation error (422 in our API) rather than raising `ArgumentError` (500).
9. **What does `normalizes` do, and why is it needed with `uniqueness`?** It cleans the value on assignment, so differently written emails compare equal and the uniqueness check can't be bypassed by changing case or spaces.
10. **Why are the sunrise and valley fixtures different?** So tests have both a deletable and a non-deletable organization.
