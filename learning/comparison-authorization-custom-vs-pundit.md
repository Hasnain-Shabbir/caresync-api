# Authorization: custom policy classes vs Pundit

A comparison to help decide how CareSync (and a team) should do role-based authorization in the GraphQL API. Related: [guide 07: roles and policies](guide-07-roles-and-policies.md).
Sources: [Pundit README](https://github.com/varvet/pundit) (gem 2.5.2). The "custom" column describes code you'd write yourself, based on the same ideas.

**Summary:** both approaches use the same idea: one **policy class per model** with a method per action, plus **default-deny**. Pundit is a small gem that standardizes the file layout and the lookup. A custom version is about 15 lines and needs no gem. The real work is the same either way: deciding the permission matrix, applying it everywhere, and testing it.

---

## 1. What each looks like

### Pundit
```ruby
# Gemfile: gem "pundit"
# app/policies/application_policy.rb  (generated by `rails g pundit:install`)
# app/policies/patient_policy.rb
class PatientPolicy < ApplicationPolicy
  def update?  = user.admin? || user.provider? || user.nurse?
  def destroy? = user.admin?
end

# In a GraphQL resolver (we are not in a controller, so we call Pundit directly):
Pundit.policy!(current_user!, patient).update?
```

### Custom (no gem)
```ruby
# app/policies/application_policy.rb  (you write it)
class ApplicationPolicy
  attr_reader :user, :record

  def initialize(user, record)
    @user = user
    @record = record
  end

  def index?   = false      # default-deny: every action is refused unless a policy says yes
  def show?    = false
  def create?  = false
  def update?  = false
  def destroy? = false
end

# app/policies/patient_policy.rb  (identical to the Pundit version)
class PatientPolicy < ApplicationPolicy
  def update?  = user.admin? || user.provider? || user.nurse?
  def destroy? = user.admin?
end

# In app/graphql/concerns/authenticatable.rb (you write the lookup):
def policy_for(record)
  klass = record.is_a?(Class) ? record : record.class
  "#{klass.name}Policy".constantize.new(current_user!, record)   # raises NameError if there is no policy
end

def authorize!(record, query)
  return true if policy_for(record).public_send(query)

  raise GraphQL::ExecutionError.new("You are not allowed to do that", extensions: { code: "FORBIDDEN" })
end
```
**The policy classes are identical in both versions.** Only the "find the right policy and call it" part differs: Pundit's `Pundit.policy!` against your `policy_for`.

## 2. Side-by-side

| Aspect | Pundit | Custom |
|---|---|---|
| New dependency | yes (one small gem, maintained, widely used) | none |
| Policy classes | `app/policies/*_policy.rb`, `user` and `record` | the same, you write `ApplicationPolicy` |
| Finding a policy for a record | `Pundit.policy!(user, record)`, handles namespaces, symbols, custom `policy_class` | your `policy_for`: 3 lines, handles only the simple `ModelPolicy` naming |
| Scopes ("which records may I see") | built-in `Scope` convention and `policy_scope` | you'd add a `Scope` class yourself, or skip it (we scope by organization anyway) |
| Missing policy | raises a clear error | raises `NameError`, equally loud |
| Default-deny | the generated `ApplicationPolicy` (verify it returns `false`) | the one you write, so you see it |
| Controller helpers (`authorize`, `verify_authorized`) | included, but we don't use them in GraphQL | not available, and not needed here |
| Unit testing a policy | plain Ruby, no gem needed | the same |
| Headless policies (no model) | supported (`authorize :dashboard, :show?`) | you'd handle symbols in `policy_for` |
| Error type | `Pundit::NotAuthorizedError` | whatever you choose (we raise `ExecutionError` directly) |
| What a new developer already knows | very likely, Pundit is the common Rails choice | has to read your 15 lines |
| What you maintain | nothing, the gem does the lookup | the lookup helper |
| Risk of subtle bugs | low, many users, long history | low, but it's your code |
| Fit with GraphQL | fine, via `Pundit.policy!` (no official GraphQL layer in this README) | equally fine |

## 3. What actually differs in practice

For **this** project the difference is small, because we only use two things from Pundit: finding the policy class and calling a method on it. Everything that matters is the same in both:

- the **permission matrix** (the design work)
- **default-deny**
- applying `authorize!` in every resolver, **after** the tenant lookup
- the **role x action test matrix** and the **coverage test** that fails if an endpoint has no entry

Pundit starts to earn its place when you need things we don't need yet: policy **scopes** used widely, headless policies, `verify_authorized` in controllers, or when your team already uses it. A custom version starts to hurt when the lookup rules grow (namespaced models, STI, custom policy classes), and you end up rebuilding Pundit.

## 4. Other options (briefly)

| Option | Idea | When it fits |
|---|---|---|
| Roles declared on each mutation (`allowed_roles %i[admin provider]`) | no policy classes, a role list per operation | few rules, **role only**. Can't express "only the patient's own provider" later |
| CanCanCan | one `Ability` class holds every rule | teams that already use it. Rules are central but the file grows large |
| Postgres row-level security | the database refuses rows | defence in depth, more setup |

## 5. How to decide

1. **Check what your company actually uses.** "Not Pundit" could mean custom code, CanCanCan, role checks in controllers, or nothing. A quick search tells you:
   ```bash
   grep -rniE "cancan|pundit|authorize|can\?|ability|role" Gemfile app | head -30
   ```
2. **A work project follows the team's convention**, and adding a new authorization gem is a team decision, not a personal one.
3. **For this learning project, you're free to choose.**

## 6. Recommendation

Use the **custom version, structured exactly like Pundit** (policy classes with `user` and `record`, default-deny, one `authorize!` helper):

- Your company doesn't use Pundit, so learning to build the pattern yourself transfers directly to what you'll see at work, and nothing about it is Pundit-specific.
- It's about 15 lines of your own code, and you understand every line (good for the interview question "how does authorization work in your API?").
- If the company or a later project adopts Pundit, **moving is easy**: your policy classes already have Pundit's shape, so you'd delete `policy_for` and call `Pundit.policy!` instead.
- You avoid a new dependency for something this small.

Choose Pundit instead if: your team wants to adopt it, you expect to need scopes and headless policies soon, or you'd rather not own the lookup code.

## 7. What changes in guide 07 if you go custom

Only the setup and the helper:
- Skip `bundle add pundit` and the generator. Write `ApplicationPolicy` yourself (section 1 above), with every method returning `false`.
- `PatientPolicy` and `OrganizationPolicy` stay exactly as written in the guide.
- In `Authenticatable`, use `policy_for` and `authorize!` from section 1 here, and use `policy_for(object).view_date_of_birth?` in the field-level rule instead of `Pundit.policy!`.
- Tests, the matrix and the coverage test are unchanged.
